## 1. تصحيح الفرضيات الأمنية وحدود التهديدات (Security Posture Correction)

### 1.1 تصحيح أمني جوهري: سرقة التوكن مقابل ركوب الجلسة (Exfiltration vs Session Riding)
* **المفهوم الخاطئ السابق:** الاعتقاد بأن تفعيل خاصية `HttpOnly` على الكوكي يوفر حماية كاملة من هجمات XSS.
* **الحقيقة الهندسية:** خاصية `HttpOnly` تمنع كود JavaScript الخبيث من **قراءة التوكن مباشرة** عبر `document.cookie` (منع سرقة التوكن Token Exfiltration). ومع ذلك، إذا وُجدت ثغرة XSS في الموقع، يستطيع كود المهاجم استدعاء مسارات النظام المحمية مثل `fetch('/api/users/delete')` داخل متصفح الضحية، وسيقوم المتصفح بإرفاق كوكي الـ `HttpOnly` تلقائياً مع الطلب (Session Riding).
* **نموذج الدفاع بالعمق المعتمد (Defense-in-Depth):**
  1. منع حقن السكربتات أصلاً عبر تقييد الـ Content Security Policy (CSP) وفلترة المدخلات.
  2. إلزام التحقق من مصادر الطلبات (Origin & Referer Validation) لجميع طلبات التعديل.
  3. تفعيل `SameSite=Lax` لمنع الهجمات العابرة للمواقع (CSRF).
  4. تخزين التجزئة المشفرة للتوكن (SHA-256) في قاعدة البيانات لمنع استخدام التوكنات المسربة من الـ Database.

| :--- | :--- | :---: | :--- |
| **S - Spoofing**<br>(انتحال الهوية) | 1. سرقة توكن الجلسة من الذاكرة المتطايرة.<br>2. هجمات القوة الغاشمة (Brute-Force) ضد الأدمن.<br>3. هجمات التخمين الموزع (Distributed Brute-Force). | **حرج (Critical)** | - كوكيز `HttpOnly; Secure; SameSite=Lax`.<br>- كبح مستدام في PostgreSQL (5 محاولات فاشلة لكل IP خلال 15 دقيقة).<br>- تأخير تصاعدي (Exponential Delay) لكل بريد يتعرض لمحاولات متكررة. |

| **R - Repudiation**<br>(إنكار العمليات) | 1. قيام مدرب بتعديل قيود لاعب صحية ثم إنكار ذلك.<br>2. محاولة إنشاء أدمن غير مصرح دون أثر. | **متوسط (Medium)** | - تسجيل كل عملية حساسة فوراً في جدول `audit_logs` متضمناً `userId` و `action` وتاريخ العملية و `ipAddress`.<br>- سكريبت أول أدمن يوثق نجاح أو فشل العملية في سجل التدقيق. |
| **I - Information Disclosure**<br>(كشف المعلومات السرية) | 1. تسريب `passwordHash` في استجابة استعلامات المستخدمين.<br>2. استغلال رسائل الخطأ لتخمين الحسابات المسجلة (User Enumeration).<br>3. طباعة بيانات الدخول في سجلات الخادم (Logs Leaks). | **حرج (Critical)** | - تجريد كائن المستخدم من أي حقول كلمات مرور برمجياً قبل إرسال الـ JSON.<br>- رسالة خطأ موحدة ومبهمة: *"بيانات الدخول غير صحيحة"*.<br>- حظر استخدام `console.log` لكلمات المرور أو الرموز البرمجية نهائياً. |
| **D - Denial of Service**<br>(حجب الخدمة) | 1. تعمد إدخال كلمة مرور خاطئة لقفل حساب الأدمن ومنعه من الدخول (Account Lockout DoS).<br>2. إجهاد قاعدة البيانات بتحديث `lastUsedAt` مع كل طلب (DB Write Flooding).<br>3. هجمات إجهاد المعالج بكلمات مرور طويلة (Bcrypt Hash Bombing). | **مرتفع (High)** | - عدم قفل حساب المستخدم تعسفياً؛ حظر الـ IP المهاجم فقط وتطبيق تأخير تصاعدي.<br>- تقييد تحديث `lastUsedAt` ليعمل دورياً (فقط إذا مر أكثر من 15 دقيقة).<br>- تحديد طول كلمة المرور بحد أقصى 128 حرفاً، مع تثبيت تكلفة Bcrypt عند Cost 10 (~80ms). |
| **E - Elevation of Privilege**<br>(تصعيد الصلاحيات) | 1. استدعاء لاعب لمسارات تخص المدربين أو الأدمن.<br>2. اختراق أفقي (IDOR): مدرب يستعرض ملف لاعب ليس مسنداً إليه في الأكاديمية. | **حرج (Critical)** | - التحقق على مستوى السيرفر من رتبة المستخدم لكل مسار API.<br>- التحقق من قيد الإسناد (`ClientCoachAssignment`) في قاعدة البيانات قبل السماح للمدرب بقراءة أو تعديل ملف اللاعب. |

## 3. تفصيل متجهات الهجوم الخاصة وحلولها الهندسية

### 3.1 معالجة خطر حجب الحساب التعسفي (Account Lockout Denial of Service)
* **السيناريو:** يقوم مهاجم بإرسال 5 طلبات فاشلة متتالية ببريد الأدمن `admin@gxacademy.com`. إذا كان النظام يقفل الحساب، يُحرم الأدمن الحقيقي من إدارة الأكاديمية!
* **التحصين:** 
  1. يتم الحظر على مستوى عنوان الـ IP المهاجم (`ipAddress`) بحجب الطلبات منه لمدة 15 دقيقة بكود `429`.
  2. الحساب نفسه يظل فعالاً ومتاحاً للدخول إذا قام الأدمن الحقيقي بتسجيل الدخول من عنوان IP موثوق.
  3. يتم تخزين المحاولات في جدول `login_attempts` في PostgreSQL مع حذف السجلات القديمة تلقائياً بعد 24 ساعة.

### 3.2 معالجة استنزاف قاعدة البيانات في دورة حياة الجلسات (DB Write Exhaustion)
* **السيناريو:** موقع رياضي يحتوي على مئات الصفحات والطلبات المتزامنة (استعراض تمارين، جداول، إشعارات). تحديث حقل `lastUsedAt` في قاعدة البيانات مع كل طلب يؤدي لاختناق PostgreSQL وزيادة زمن الاستجابة (Latency).
* **التحصين:** 
  - السيرفر يتحقق من صحة الجلسة عبر القراءة السريعة (`SELECT`).
  - تحديث `lastUsedAt` يتم تقييده برمجياً: **لا يتم تنفيذ أمر `UPDATE` إلا إذا كان الفارق بين الوقت الحالي و `lastUsedAt` أكثر من 15 دقيقة**.
  - تطبيق مهلة انتهاء مطلقة (Absolute Session Lifetime) مدتها 14 يوماً لا يمكن تجاوزها، ومهلة عدم نشاط (Idle Timeout) مدتها 48 ساعة.

### 3.3 معالجة ثغرات الوصول غير المصرح به للبيانات (IDOR & Horizontal Escalation)
* **السيناريو:** مدرب برتبة `COACH` يطلب `/api/clients/client-xyz`. هذا العميل مسند لمدرب آخر في الأكاديمية.
* **التحصين:** 
  - فحص السيرفر الداخلي:
    ```ts
    if (session.user.role === "COACH") {
      const isAssigned = await prisma.clientCoachAssignment.findFirst({
        where: { coachId: session.user.coachId, clientId: targetClientId, isActive: true }
      });
      if (!isAssigned) return NextResponse.json({ error: "Forbidden" }, { status: 403 });
    }
    ```
  - اللاعب لا يمكنه إطلاقاً طلب أي معرف غير المعرف الشخصي المسند له (`clientId === session.user.clientId`).

## 4. مصفوفة الثوابت الأمنية الحتمية (Security Invariants v2.0)

1. **الثابت 1:** لا توجد أسرار نصية صريحة في أي مكان (كلمات المرور مشفرة بـ Bcrypt، ورموز الجلسات مشفرة بـ SHA-256).
2. **الثابت 2:** لا اعتماد على واجهة العميل في الصلاحيات (الرتبة والملكية تُقرأ من PostgreSQL في كل استدعاء).
3. **الثابت 3:** الإبطال الفوري والشامل (تسجيل الخروج أو تغيير كلمة المرور يُلغي الجلسات في قاعدة البيانات ومسح الكوكي فوراً).
4. **الثابت 4:** الأمان الوقائي لتهيئة الأدمن (العملية مستقلة، تفاعلية، لا تعمل تلقائياً، وتُلغى إذا وجد أي أدمن سابق).
5. **الثابت 5:** عزل بيانات المتصفح التجريبية (لا يحصل أي مستخدم محلي على أي جلسة في السيرفر).
